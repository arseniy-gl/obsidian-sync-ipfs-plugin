# Плагин сообщества Obsidian

## Обзор проекта

-   Цель: Плагин сообщества Obsidian (TypeScript → скомпилированный JavaScript).
-   Точка входа: `src/main.ts`, компилируемый в `main.js` и загружаемый Obsidian.
-   Необходимые артефакты релиза: `main.js`, `manifest.json` и опционально `styles.css`.

## Среда и инструменты

-   Node.js: используйте текущую LTS-версию (рекомендуется Node 18+).
-   **Менеджер пакетов: npm** (требуется для этого примера — `package.json` определяет npm-скрипты и зависимости).
-   **Сборщик: esbuild** (требуется для этого примера — `esbuild.config.mjs` и скрипты сборки зависят от него). Альтернативные сборщики, такие как Rollup или webpack, допустимы для других проектов, если они собирают все внешние зависимости в `main.js`.
-   Типы: определения типов `obsidian`.

**Примечание**: Этот пример проекта имеет специфические технические зависимости от npm и esbuild. Если вы создаете плагин с нуля, вы можете выбрать другие инструменты, но вам нужно будет соответствующим образом заменить конфигурацию сборки.

### Установка

```bash
npm install
```

### Разработка (с отслеживанием изменений)

```bash
npm run dev
```

### Сборка для продакшена

```bash
npm run build
```

## Линтинг

-   Чтобы использовать eslint, установите его из терминала: `npm install -g eslint`
-   Чтобы проанализировать этот проект с помощью eslint, используйте эту команду: `eslint src/main.ts`
-   Затем eslint создаст отчет с предложениями по улучшению кода по файлам и номерам строк.
-   Если ваш исходный код находится в папке, например `src`, вы можете использовать eslint с этой командой для анализа всех файлов в этой папке: `eslint ./src/`

## Соглашения о файлах и папках

-   **Организуйте код в несколько файлов**: Разделяйте функциональность по отдельным модулям, а не помещайте все в `main.ts`.
-   Исходный код находится в `src/`. `main.ts` должен быть небольшим и сосредоточенным на жизненном цикле плагина (загрузка, выгрузка, регистрация команд).
-   **Пример структуры файлов**:
    ```
    src/
      __tests__/        # Файлы тестов
      main.ts           # Точка входа плагина, управление жизненным циклом
      settings.ts       # Интерфейс и значения по умолчанию для настроек
      commands/         # Реализации команд
        command1.ts
        command2.ts
      ui/              # Компоненты пользовательского интерфейса, модальные окна, представления
        modal.ts
        view.ts
      utils/           # Вспомогательные функции, утилиты
        helpers.ts
        constants.ts
      types.ts         # Интерфейсы и типы TypeScript
    ```
-   **Не коммитьте артефакты сборки**: Никогда не добавляйте в систему контроля версий `node_modules/`, `main.js` или другие сгенерированные файлы.
-   Плагин должен быть небольшим. Избегайте больших зависимостей. Предпочитайте пакеты, совместимые с браузером.
-   Сгенерированный вывод должен размещаться в корне плагина или в `dist/` в зависимости от вашей настройки сборки. Артефакты релиза должны находиться на верхнем уровне папки плагина в хранилище (`main.js`, `manifest.json`, `styles.css`).

## Правила манифеста (`manifest.json`)

-   Должен включать (не исчерпывающий список):
    -   `id` (идентификатор плагина; для локальной разработки он должен совпадать с именем папки)
    -   `name`
    -   `version` (семантическое версионирование `x.y.z`)
    -   `minAppVersion`
    -   `description`
    -   `isDesktopOnly` (логическое значение)
    -   Опционально: `author`, `authorUrl`, `fundingUrl` (строка или карта)
-   Никогда не изменяйте `id` после релиза. Относитесь к нему как к стабильному API.
-   Поддерживайте `minAppVersion` в актуальном состоянии при использовании новых API.
-   Канонические требования закодированы здесь: https://github.com/obsidianmd/obsidian-releases/blob/master/.github/workflows/validate-plugin-entry.yml

## Тестирование

-   Ручная установка для тестирования: скопируйте `main.js`, `manifest.json`, `styles.css` (если есть) в:
    ```
    <Vault>/.obsidian/plugins/<plugin-id>/
    ```
-   Перезагрузите Obsidian и включите плагин в **Настройки → Сторонние плагины**.

## Команды и настройки

-   Любые команды, предназначенные для пользователя, должны добавляться через `this.addCommand(...)`.
-   Если плагин имеет конфигурацию, предоставьте вкладку настроек и разумные значения по умолчанию.
-   Сохраняйте настройки с помощью `this.loadData()` / `this.saveData()`.
-   Используйте стабильные идентификаторы команд; избегайте их переименования после релиза.

## Версионирование и релизы

-   Увеличьте `version` в `manifest.json` (SemVer) и обновите `versions.json`, чтобы сопоставить версию плагина с минимальной версией приложения.
-   Создайте релиз на GitHub, тег которого точно соответствует `version` в `manifest.json`. Не используйте префикс `v`.
-   Прикрепите `manifest.json`, `main.js` и `styles.css` (если есть) к релизу в качестве отдельных ассетов.
-   После первоначального релиза следуйте процессу добавления/обновления вашего плагина в каталоге сообщества по мере необходимости.

## Безопасность, конфиденциальность и соответствие требованиям

Следуйте **Политикам для разработчиков** и **Руководствам по плагинам** Obsidian. В частности:

-   По умолчанию работайте локально/офлайн. Делайте сетевые запросы только тогда, когда это необходимо для функции.
-   Никакой скрытой телеметрии. Если вы собираете необязательную аналитику или вызываете сторонние сервисы, требуйте явного согласия и четко документируйте это в `README.md` и в настройках.
-   Никогда не выполняйте удаленный код, не загружайте и не выполняйте скрипты, а также не обновляйте код плагина автоматически вне обычных релизов.
-   Минимизируйте область действия: читайте/записывайте только то, что необходимо внутри хранилища. Не получайте доступ к файлам за пределами хранилища.
-   Четко раскрывайте информацию о любых используемых внешних сервисах, отправляемых данных и рисках.
-   Уважайте конфиденциальность пользователей. Не собирайте содержимое хранилища, имена файлов или личную информацию, если это не является абсолютно необходимым и на это не было дано явного согласия.
-   Избегайте обманных паттернов, рекламы или спам-уведомлений.
-   Регистрируйте и очищайте все слушатели DOM, приложения и интервалов с помощью предоставленных хелперов `register*`, чтобы плагин выгружался безопасно.

## Рекомендации по UX и тексту (для текста в интерфейсе, команд, настроек)

-   Предпочитайте использовать заглавную букву как в предложении для заголовков, кнопок и названий.
-   Используйте четкие, ориентированные на действие повелительные наклонения в пошаговых инструкциях.
-   Используйте **жирный шрифт** для обозначения буквальных меток интерфейса. Предпочитайте "выбрать" для взаимодействий.
-   Используйте стрелочную нотацию для навигации: **Настройки → Сторонние плагины**.
-   Строки в приложении должны быть короткими, последовательными и без жаргона.

## Производительность

-   Запуск должен быть легким. Откладывайте тяжелую работу до тех пор, пока она не понадобится.
-   Избегайте длительных задач во время `onload`; используйте ленивую инициализацию.
-   Пакетный доступ к диску и избегайте чрезмерного сканирования хранилища.
-   Используйте debounce/throttle для дорогостоящих операций в ответ на события файловой системы.

## Соглашения о кодировании

-   Предпочтителен TypeScript с `"strict": true`.
-   **`main.ts` должен быть минимальным**: Сосредоточьтесь только на жизненном цикле плагина (onload, onunload, вызовы addCommand). Делегируйте всю логику функций в отдельные модули.
-   **Разделяйте большие файлы**: Если какой-либо файл превышает ~200-300 строк, рассмотрите возможность его разделения на более мелкие, сфокусированные модули.
-   **Используйте четкие границы модулей**: Каждый файл должен иметь одну, четко определенную ответственность.
-   Соберите все в `main.js` (без несвязанных зависимостей времени выполнения).
-   Избегайте API Node/Electron, если вам нужна мобильная совместимость; установите `isDesktopOnly` соответствующим образом.
-   Предпочитайте `async/await` цепочкам промисов; обрабатывайте ошибки корректно.

## Мобильные устройства

-   По возможности тестируйте на iOS и Android.
-   Не предполагайте поведение только для настольных компьютеров, если `isDesktopOnly` не равно `true`.
-   Избегайте больших структур в памяти; помните об ограничениях памяти и хранилища.

## Что делать и чего не делать агенту

**Делать**
-   Добавляйте команды со стабильными идентификаторами (не переименовывайте после релиза).
-   Предоставляйте значения по умолчанию и валидацию в настройках.
-   Пишите идемпотентные пути кода, чтобы перезагрузка/выгрузка не приводила к утечке слушателей или интервалов.
-   Используйте хелперы `this.register*` для всего, что требует очистки.

**Не делать**
-   Вводить сетевые вызовы без очевидной для пользователя причины и документации.
-   Поставлять функции, требующие облачных сервисов, без четкого раскрытия информации и явного согласия.
-   Хранить или передавать содержимое хранилища, если это не является необходимым и на это не было дано согласия.

## Общие задачи

### Организация кода по нескольким файлам

**main.ts** (минимальный, только жизненный цикл):
```ts
import { Plugin } from "obsidian";
import { MySettings, DEFAULT_SETTINGS } from "./settings";
import { registerCommands } from "./commands";

export default class MyPlugin extends Plugin {
  settings: MySettings;

  async onload() {
    this.settings = Object.assign({}, DEFAULT_SETTINGS, await this.loadData());
    registerCommands(this);
  }
}
```

**settings.ts**:
```ts
export interface MySettings {
  enabled: boolean;
  apiKey: string;
}

export const DEFAULT_SETTINGS: MySettings = {
  enabled: true,
  apiKey: "",
};
```

**commands/index.ts**:
```ts
import { Plugin } from "obsidian";
import { doSomething } from "./my-command";

export function registerCommands(plugin: Plugin) {
  plugin.addCommand({
    id: "do-something",
    name: "Do something",
    callback: () => doSomething(plugin),
  });
}
```

### Добавление команды

```ts
this.addCommand({
  id: "your-command-id",
  name: "Do the thing",
  callback: () => this.doTheThing(),
});
```

### Сохранение настроек

```ts
interface MySettings { enabled: boolean }
const DEFAULT_SETTINGS: MySettings = { enabled: true };

async onload() {
  this.settings = Object.assign({}, DEFAULT_SETTINGS, await this.loadData());
  await this.saveData(this.settings);
}
```

### Безопасная регистрация слушателей

```ts
this.registerEvent(this.app.workspace.on("file-open", f => { /* ... */ }));
this.registerDomEvent(window, "resize", () => { /* ... */ });
this.registerInterval(window.setInterval(() => { /* ... */ }, 1000));
```

## Устранение неполадок

-   Плагин не загружается после сборки: убедитесь, что `main.js` и `manifest.json` находятся на верхнем уровне папки плагина в `<Vault>/.obsidian/plugins/<plugin-id>/`.
-   Проблемы со сборкой: если `main.js` отсутствует, запустите `npm run build` или `npm run dev` для компиляции исходного кода TypeScript.
-   Команды не появляются: убедитесь, что `addCommand` выполняется после `onload` и что идентификаторы уникальны.
-   Настройки не сохраняются: убедитесь, что `loadData`/`saveData` ожидаются и что вы перерисовываете интерфейс после изменений.
-   Проблемы только на мобильных устройствах: убедитесь, что вы не используете API только для настольных компьютеров; проверьте `isDesktopOnly` и исправьте.
